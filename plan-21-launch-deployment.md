# Afghan Pride — Launch & store deployment (Android, iOS, Web)

This document is the **canonical checklist** for shipping the app on all three Flutter targets. **QA, testing, and backup QA** live in **`plan-08-qa-release.md`**. **Store consoles** (Google Play, App Store Connect) own listing copy, graphics, and compliance forms—the repo owns **builds, versioning, env wiring, and in-app branding**.

**Related docs:** `TESTING.md` (build commands + device QA), `plan-08-qa-release.md` (QA layers, release checklist, operational QA), `plan-20-flutter-tooling-and-environments.md` (dev/staging/prod `dart-define` / flavors), `plan-07-hosting-devops.md` (API + hosting), `AGENTS.md` (secrets, no service role in client).

**Product-facing name:** the shipped display name is **Pride** (launcher, PWA manifest, in-app `appTitle`). Internal package id may remain `pride_v3` / `com.pridev3.pride_v3` until you intentionally migrate bundle IDs.

## 1. Versioning and release builds (all platforms)

- **Semantic version + build number:** keep `version:` in `pubspec.yaml` accurate (`major.minor.patch+build`). Android maps **build-name → versionName**, **build-number → versionCode**; iOS maps similarly to **CFBundleShortVersionString** / **CFBundleVersion** when built with Flutter.
- **Environment:** production Play/App Store/Web builds must use **production** API and Supabase public values only, via **`--dart-define` (or flavors)** per `plan-20`. Never embed production secrets; anon keys only in the client.
- **Commands (see also `TESTING.md`):**
  - Web: `flutter build web` (add `--dart-define=...` as documented for prod). Output: `build/web/`.
  - Android **AAB for Play** (preferred over APK for store): `flutter build appbundle` (with same defines). Output under `build/app/outputs/bundle/release/`.
  - Android APK (side-load / QA): `flutter build apk`.
  - iOS: build on macOS with Xcode or `flutter build ipa` after signing is configured in the workspace.

## 2. Branding assets in this repo (`pride_full_platform_icon_pack`)

Keep this folder as the **single source** for regenerating store and in-app icons:

| Subfolder | Typical use |
|-----------|-------------|
| `android_adaptive/` | Adaptive foreground/background (432×432 safe zone) + legacy density PNGs for pre–API 26 fallbacks |
| `web/` | PWA / favicon sizes (e.g. 192, 512); copied into `web/icons/` and `web/favicon.png` as part of release prep when art changes |
| `ios/` | Master **1024×1024** (`icon_1024.png`) to regenerate **all** `AppIcon.appiconset` sizes (@2x/@3x), because the smaller named files in the pack are often @1× logical sizes only |
| `macos.iconset/`, `windows/` | Desktop targets if you later ship them |

**Play / App Store graphics** (feature graphic, phone/tablet screenshots, “promotional” images) are **not** fully generated by Flutter; export or design them from the same brand kit and upload in each console. Minimum: **high-res app icon** (Play: 512×512; Apple: 1024×1024 marketing icon) plus **phone screenshots** for primary locales.

## 3. Google Play (Android)

1. **Developer account** — one-time registration; accept Play policies.
2. **Create app** — default language, app name (**Pride**), free/paid, declarations (ads, news app, COVID-19, etc.) answered honestly.
3. **Signing** — use **Play App Signing** (recommended). Upload key in CI or local machine; Play holds the app signing key. Ensure `flutter build appbundle` uses your **upload keystore** consistently (document alias/password in a secrets manager, not in git).
4. **Release track** — start with **internal testing** → **closed/open testing** → **production** when QA passes (`plan-08-qa-release.md`).
5. **Store listing** — short description, full description, screenshots (phone required; 7" tablet optional but useful), **feature graphic** (1024×500), icon. Localize if you ship multiple countries/languages.
6. **Data safety** — questionnaire must match what the app **actually** collects (accounts, financial info, photos, device IDs, crash logs, etc.). Update when permissions or SDKs change.
7. **Privacy policy** — public HTTPS URL required when you collect user data or use sensitive APIs; keep it in sync with the app behavior.
8. **Target API / policy** — meet Google’s **target API level** requirements for new updates and declarations (e.g. photo picker, scoped storage) as they evolve.
9. **Countries & pricing** — set distribution and any subscriptions per `plan-06` when billing goes live.

**After upload:** use **staged rollouts** (e.g. 5% → 20% → 100%) for risky releases; monitor **Android vitals** (ANRs, crashes) and user reviews.

## 4. Apple App Store (iOS)

1. **Apple Developer Program** — paid membership; create **App ID** / bundle identifier consistent with Xcode (`ios/Runner.xcodeproj`).
2. **App Store Connect** — new app record; bundle id; SKU; primary language; user-facing name **Pride**.
3. **Certificates & provisioning** — development + **Distribution** profiles; enable **Sign in with Apple** only if you use it (this product uses custom API auth per plans—don’t enable unused capabilities).
4. **Archive & upload** — Xcode **Product → Archive** → **Distribute App** to App Store Connect, or `flutter build ipa` with correct signing. First builds often go to **TestFlight** for internal/external testers.
5. **App Privacy** — nutrition labels must match data collection (account, diagnostics, etc.).
6. **Encryption / export compliance** — answer **export compliance** questions (many apps qualify for standard HTTPS-only exemption; confirm with legal if unsure).
7. **Review** — provide **demo account** credentials if login is required; notes for reviewers (offline mode, license screen, etc.).
8. **Screenshots** — required sizes per device class; use real device or simulator captures for **RTL locales** if you market in those regions.

**Windows-only dev note (`AGENTS.md`):** keep **iOS compile-clean** from Windows/CI; run Archive/TestFlight on a **Mac** before each App Store submission.

## 5. Web (PWA / static hosting)

1. **Build:** `flutter build web` with **production** `dart-define` values. If the site is not served from domain root, pass **`--base-href=/your-path/`** so asset URLs resolve.
2. **Host** — upload **`build/web/`** to a static host (e.g. **Cloudflare Pages**, **Firebase Hosting**, **Netlify**, **Vercel**, or object storage + CDN). Use **HTTPS** and a **custom domain** for production.
3. **PWA** — `web/manifest.json` and icons control **install** name and theme; keep **name** / **short_name** aligned with **Pride** for store-like consistency when users “Add to Home Screen.”
4. **API & CORS** — if the web app calls the NestJS API from a browser, the API must allow the **web origin** in CORS for staging/prod as applicable (`plan-04` / server config).
5. **Caching** — after deploy, verify **service worker** / cache behavior: users should get new bundles after a release (hard refresh or cache-busting strategy if you hit stale-asset issues).
6. **Smoke checks** — Lighthouse (performance, PWA, accessibility), **RTL** layout on web for supported locales, and **login + license** flows per the Web QA scope in `plan-08-qa-release.md`.

## 6. Cross-platform checklist before first public launch

- [ ] **QA** — device QA + web QA in `plan-08-qa-release.md` completed for the release candidate.
- [ ] **Backend** — production API + Supabase project live; migrations applied; monitoring/alerts (`plan-07`).
- [ ] **Legal / policy** — privacy policy URL live; Play **Data safety** + Apple **App Privacy** accurate.
- [ ] **Support path** — email or in-app link for shop owners (even if lightweight).
- [ ] **Crash / stability (recommended)** — integrate **Firebase Crashlytics** or **Sentry** (or equivalent) for mobile + optionally web; symbolicate iOS/Android dSYMs / mapping files per vendor docs.
- [ ] **Analytics (optional)** — if used, disclose in policies; minimize PII.
- [ ] **Deep links / intent filters** — if you add universal links or app links later, test per platform before marketing URLs.
- [ ] **Subscriptions / license** — when live, ensure server time, grace periods, and read-only mode match `plan-06` and store subscription SKUs (if any) match backend.

## 7. Post-launch operations

- **Gradual rollout** on Play; **phased release** / TestFlight on Apple where applicable.
- **Hotfixes:** bump **build number** immediately; cherry-pick or fast-forward main; rebuild AAB/IPA/web; document each hotfix in internal changelog.
- **Schema migrations:** follow `plan-02` / `plan-03` for Isar migrations and server compatibility so old app versions do not corrupt data.

## 8. Optional hardening (affects all platforms over time)

- **CI:** build `apk`/`appbundle`/`web` on tags; optional **iOS** build on macOS runners; run `flutter analyze` + `flutter test`.
- **Code signing in CI:** store keystore / API keys as **encrypted secrets** (GitHub Actions, etc.).
- **Supply-chain:** dependabot / `flutter pub outdated` discipline; review native SDK updates (camera, file picker) for permission regressions.
- **Accessibility:** WCAG-minded checks on web; TalkBack / VoiceOver passes on mobile for critical flows (orders, payments, subscription).
